# Sniffer Core Benchmark v1

本文档冻结 `sniffer-core` 第一版可重复基准的测试口径和一次参考运行结果。结果对应与本文档
一同提交的源码，仅用于建立后续优化的基线；不同硬件、文件系统、编译器和 Arrow 版本之间
不应直接比较绝对耗时。

## 测试环境

- 日期：2026-09-16
- CPU：Apple M4
- 逻辑 CPU：10
- 操作系统：macOS 26.6.2（25G83）
- 架构：arm64
- 编译器：Apple Clang 21.0.0
- Arrow C++：23.0.1
- 构建模式：Release
- 执行方式：单线程

构建命令：

```bash
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release
cmake --build build-release -j4
```

## 对照格式与计时口径

两个 benchmark 都比较以下三种格式：

- `sniffer`：Sniffer Segment，使用当前确定性编码选择器、Row Group 元数据、索引和 checksum；
- `arrow_ipc`：未压缩 Arrow IPC file；
- `arrow_ipc_zstd`：使用 ZSTD 的 Arrow IPC file。

Arrow IPC 的压缩和解压关闭内部多线程。所有输入在计时前构造，所有格式使用相同输入和相同
Row Group/RecordBatch 切分。多次执行后分别报告各阶段的中位数；文件大小是确定值。

这里测量的是文件级全链路，而不是纯 codec 微基准：写入时间包括编码、元数据和 checksum
生成以及文件写入，读取时间包括文件读取、格式解析、校验和解码。临时文件位于系统临时目录，
重复读取可能命中操作系统页缓存。

## 性能 benchmark

复现命令：

```bash
./build-release/sniffer_core_performance_benchmark \
  --rows=100000 \
  --iterations=7 \
  --row-group=8192
```

输入包含递增 `id`、32 个值的 `group` 字符串和每 17 行一个 null 的线性 `value`。查询条件为
`id >= 50000`，投影 `id,value`，选择率为 50%。Arrow IPC 对照使用类型化循环执行相同过滤和
投影物化，但不模拟 Sniffer 的索引与 checksum。

| 格式 | 写入 ms | 写入 rows/s | 扫描 ms | 扫描 rows/s | 端到端 ms | 端到端 rows/s | 文件字节 |
|---|---:|---:|---:|---:|---:|---:|---:|
| Sniffer | 72.9057 | 1,371,630 | 18.9773 | 5,269,440 | 91.4441 | 1,093,560 | 675,943 |
| Arrow IPC | 1.29829 | 77,024,300 | 0.830000 | 120,482,000 | 2.08967 | 47,854,500 | 2,785,530 |
| Arrow IPC + ZSTD | 3.22933 | 30,966,100 | 1.83229 | 54,576,500 | 5.06525 | 19,742,400 | 485,226 |

Sniffer 扫描观察指标：13 个 Row Group 中剪枝 6 个，读取 14 个 ColumnChunk，共 184,036 字节，
输出 50,000 行。各阶段独立取中位数，因此端到端中位数不一定严格等于写入和扫描中位数之和。

这次运行中，Sniffer 文件比未压缩 Arrow IPC 小约 75.7%，但比 Arrow IPC + ZSTD 大约 39.3%。
索引剪枝已经生效，但当前 writer/reader 全链路速度仍明显慢于两个 Arrow IPC 对照。

## 压缩 benchmark

复现命令：

```bash
./build-release/sniffer_core_compression_benchmark \
  --rows=100000 \
  --iterations=5 \
  --row-group=8192
```

每个场景包含一个 Arrow 列。`logical_bytes` 是输入 RecordBatch 引用的去重 Arrow buffer 总大小，
不含 schema 和文件级元数据。压缩比定义为 `logical_bytes / file_bytes`，大于 1 表示文件小于
逻辑数据；MiB/s 按逻辑字节数计算。每轮读取后执行完整 Arrow batch 一致性检查，但检查本身、
输入构造和文件大小查询不计时。

### 合计结果

| 格式 | 逻辑字节 | 文件字节 | 压缩比 | 编码写入 ms | 写入 MiB/s | 解码读取 ms | 读取 MiB/s |
|---|---:|---:|---:|---:|---:|---:|---:|
| Sniffer | 7,181,258 | 3,622,610 | 1.98234 | 86.9556 | 78.7595 | 51.3035 | 133.492 |
| Arrow IPC | 7,181,258 | 7,198,324 | 0.997629 | 2.11971 | 3,230.90 | 1.74012 | 3,935.69 |
| Arrow IPC + ZSTD | 7,181,258 | 2,658,852 | 2.70089 | 7.16471 | 955.877 | 4.70558 | 1,455.42 |

合计耗时是六个场景各自中位耗时之和。Sniffer 文件是未压缩 Arrow IPC 的 50.3%，是 Arrow
IPC + ZSTD 的 136.2%。Sniffer 在长 RLE、nullable 偏斜整数和低基数字符串上具有明显的专用
编码优势；高基数随机字符串会膨胀，表明编码选择器仍需要更严格的 Plain 回退成本判断。

## v1 已知限制与后续方向

- 数据量较小，读取结果容易受页缓存影响；后续应增加超过可用内存的数据集和冷缓存测试。
- 当前结果混合 codec、格式、checksum、分配和文件 I/O 成本，不能用于证明某个 codec 本身
  快于或慢于 ZSTD；若要验证字节内 codec，应增加独立的内存微基准。
- 当前仅覆盖合成分布；后续应增加来自实际工作负载、宽表和多列相关性的数据集。
- 性能 benchmark 的 Arrow IPC 路径没有与 Sniffer 完全等价的索引和校验语义，因此它是工程
  基线，而不是功能完全对等的格式比较。
- v1 不记录耗时方差和分位数。后续版本可输出每轮原始数据、P50/P95 和稳定性指标。
